Getting Started

Requirements, running the app, the checks and a release build of a generated project.

Generate a project

Projects are generated on your machine by the cmpose MCP server (github.com/whinstudio/cmpose). In Claude Code: claude mcp add -s user cmpose -- npx -y @cmpose/mcp (Node.js 20+ and git), then ask your agent for an app. cmp_describe lists the options; cmp_generate takes the project name, app name, package, output folder, templateType (showcase or blank), features (your own modules), featuresConfig (blank only: network, theming, multiLang, room, detekt, purchases, ads, backend and the rest) and ci. For a standalone server, backend_describe and backend_generate create a Kotlin/Ktor backend (Docker-ready) with an optional sharing part.

Requirements

The generated README.md lists the exact versions: JDK, Kotlin, Compose Multiplatform, AGP, Gradle, Android SDK levels and the iOS minimum. Gradle runs on JDK 21 and downloads it when it is missing. iOS needs Xcode 16 or newer, and the iOS targets are arm64 only (an Apple Silicon Mac or a device).

Run

Android: ./gradlew :androidApp:installDebug. iOS: open iosApp/iosApp.xcodeproj in Xcode and run. On a device, set TEAM_ID in Config.xcconfig. It only picks the signing team: the bundle ID stays your package name, the ID to register in Firebase and App Store Connect. If you write a new module by hand, apply the KMP library plugin before the Compose convention (the generated modules already do).

Checks

./gradlew detekt runs the static analysis and ./gradlew allTests every test.

CI (optional)

Generate with the CI option (ci: true in cmp_generate) to get .github/workflows/ci.yml. It runs detekt (when the project has it), the unit tests and the Android and iOS builds on every pull request, and by hand from the Actions tab (workflow_dispatch); pushes to main do not start it. The iOS job runs on a macOS runner, which GitHub bills at a higher rate. Without the option the project has no .github/ folder.

Release

Release builds are minified with R8 and use androidApp/proguard-rules.pro. Copy keystore.properties.example to keystore.properties (kept out of git) to sign the build; without it the release build is unsigned. Set the production API address as described in Networking → Base URL.

Modular Navigation

Learn how to implement type-safe navigation with modular architecture using Compose Navigation.

Navigation

Our navigation system is designed for modularity. Each feature module has a contract module where destinations are defined. To navigate to a screen in another module, you only need to implement that module's contract.

1. Define Destination (Contract Module)

In the feature's contract module (Screens.kt), define a destination implementing NavigationCommand.Destination: a data object for a screen without arguments, a data class for a screen with arguments. Every generated feature module has a data object <Module>Destination; the showcase's HomeScreenDestination carries a username, which HomeViewModel reads back from its SavedStateHandle by the property's name, savedStateHandle[HomeScreenDestination::githubUsername.name] (toRoute<HomeScreenDestination>() works in the app too, but decodes through an Android Bundle that the JVM unit tests do not have).

Screens.kt 
// feature/onboarding/contract: no arguments
@Serializable
data object SettingsDestination : NavigationCommand.Destination

// feature/home/contract: with arguments (showcase)
@Serializable
data class HomeScreenDestination(val githubUsername: String) : NavigationCommand.Destination

2. Provide Navigation Graph (Presentation Module)

Implement NavGraphProvider to register your screen. The @Named annotation is crucial for Koin to distinguish between multiple providers. (Every generated feature module has a <Module>Provider opening <Module>ScreenRoute(), and a <Module>Entry that lists it on a blank app's start screen.)

HomeProvider.kt 
@Single(binds = [NavGraphProvider::class])
@Named("HomeProvider")
internal class HomeProvider : NavGraphProvider {
    override fun registerGraph(provider: NavGraphBuilder) {
        provider.apply {
            composable<HomeScreenDestination> {
                HomeScreenRoute()
            }
        }
    }
}

4. Navigation Manager

The NavigationManager interface handles navigation commands via a Flow.

NavigationManager.kt 
interface NavigationManager {
    val navigationCommandFlow: Flow<NavigationCommand>
    fun navigate(navigationCommand: NavigationCommand)
}

// NavigationCommand.kt
sealed interface NavigationCommand {
    interface Destination : NavigationCommand
    data class NavigateTo(
        val to: Destination,
        val clearBackStack: Boolean = false,
        val addToBackStack: Boolean = true
    ) : NavigationCommand
    data object NavigateUp : NavigationCommand
    data class PopBackStackTo(val to: Destination, val inclusive: Boolean = false) : NavigationCommand
}

5. Handle Navigation Events

Collect the navigation flow in your main screen to trigger actual navigation actions.

NavigationLaunchedEffect.kt 
@Composable
internal fun NavigationLaunchedEffect(
    navigationManager: NavigationManager,
    navController: NavController
) {
    LaunchedEffect(key1 = Unit) {
        navigationManager.navigationCommandFlow.collect { command ->
            when (command) {
                NavigationCommand.NavigateUp -> navController.navigateUp()
                is NavigationCommand.PopBackStackTo -> navController.popBackStack(route = command.to, inclusive = command.inclusive)
                is NavigationCommand.NavigateTo -> navController.navigate(route = command.to) {
                    if (command.clearBackStack) {
                        popUpTo(navController.graph.id) { inclusive = true }
                    } else if (!command.addToBackStack) {
                        navController.currentDestination?.id?.let { popUpTo(it) { inclusive = true } }
                    }
                }
                is NavigationCommand.Destination -> navController.navigate(route = command)
            }
        }
    }
}

NavigateTo(to, clearBackStack = true) makes the destination the only entry on the back stack (for example login → home, where Back should leave the app). NavigateTo(to, addToBackStack = false) replaces the current screen instead of stacking on top of it.

Deep links

Every generated app opens links with its own scheme, taken from the project name; there is no generator option for it.

The scheme

The scheme is your project's name in lower case: a project named MyApp opens myapp:// links. The generator writes it in three places that must stay in step: DEEP_LINK_SCHEME in core/navigation/.../DeepLinkConfig.kt, the android:scheme of MainActivity's intent filter in AndroidManifest.xml, and CFBundleURLSchemes in iosApp/iosApp/Info.plist. Android (onCreate and onNewIntent, launchMode="singleTask") and iOS (.onOpenURL in iOSApp.swift) both hand the link to the same Kotlin handleDeepLink(uri); DeepLinkHandler matches it to a route and navigates through the NavigationManager, like any other screen.

  • Showcase: myapp://user/{username} opens that GitHub profile on Home (a name that is not a valid GitHub username just opens the app), and myapp://settings opens Settings.
  • Blank: myapp:// opens the start screen; every custom module has its own path, its name: myapp://orders for a module named orders.
  • A path no route knows just opens the app. If two routes have the same path, the first one wins and a warning is logged.

Adding a route

A link maps to a screen through a DeepLinkRoute, registered with Koin like a FeatureEntry. Its pattern is the path after the scheme; a {name} segment is a parameter. destination(arguments) returns the screen's destination, or null when an argument is not valid. Links come from outside the app: check every argument before you use it.

OrderDeepLink.kt 
// feature/orders/presentation/.../navigation/OrderDeepLink.kt
// myapp://orders/42 opens order 42
@Single(binds = [DeepLinkRoute::class])
@Named("OrderDeepLink")
internal class OrderDeepLink : DeepLinkRoute {
    override val pattern: String = "orders/{id}"

    override fun destination(arguments: Map<String, String>): NavigationCommand.Destination? =
        arguments["id"]
            ?.toLongOrNull()
            ?.let { OrderDetailDestination(orderId = it) }
}

Every generated feature module already has one: <Module>DeepLink in its presentation module's navigation package, with the module's name as its path. Add a {id} segment there to open a single item.

Trying a link

With the app installed on a running emulator or simulator:

Terminal

# iOS simulator

App Links and Universal Links

https links to your own domain are ready but off (APP_LINK_HOST = ""). Turning them on takes three steps together:

  1. Set APP_LINK_HOST in DeepLinkConfig.kt to your domain (e.g. example.com).
  2. Android: uncomment the autoVerify intent filter in AndroidManifest.xml with your host, and serve https://example.com/.well-known/assetlinks.json with your package name and your signing certificate's SHA-256 (keytool -list -v -keystore …; with Play App Signing, the Play Console shows it).
  3. iOS: serve https://example.com/.well-known/apple-app-site-association (applinks → your TEAMID.bundleId), copy iosApp/Configuration/UniversalLinks.entitlements.example to iosApp/iosApp/iosApp.entitlements with your domain, add CODE_SIGN_ENTITLEMENTS = iosApp/iosApp.entitlements to Config.xcconfig and enable Associated Domains for the App ID.

Then https://example.com/settings opens the same route as myapp://settings.

Scheme collisions

A custom scheme is not owned by anyone: another app may claim the same one. For a more unique scheme, use your package name (e.g. com.example.app) in DeepLinkConfig.kt, AndroidManifest.xml and Info.plist together, or turn on App Links and Universal Links, which only your domain can claim.

Dependency Injection

We use Koin with auto-annotation for efficient and scalable dependency injection.

1. Create a Module

To create a new Koin module, define a class annotated with @Module and @ComponentScan. This tells Koin to scan the specified package for annotated components. (Feature packages are <your.package>.feature.<module>.<layer> in both templates, e.g. @ComponentScan("com.example.myapp.feature.home.presentation").)

HomePresentationModule.kt 
@Module
@ComponentScan("com.example.myapp.feature.home.presentation")
class HomePresentationModule

2. Register the Module

Add your module to appModules() in the shared module (shared/src/commonMain/.../di/initKoin.kt); initKoin starts Koin with that list.

initKoin.kt 
// The platform entry points start Koin: Android's Application, iOS's startKoinAtLaunch().
fun initKoin(
    isDebug: Boolean,
    config: KoinAppDeclaration? = null
) {
    startKoin {
        config?.invoke(this)
        modules(module { single { BuildEnvironment(isDebug) } })
        modules(appModules())
    }
}

// ...

fun appModules(): List<KoinModule> = buildList {
    add(NavigationModule().module)
    add(OnboardingPresentationModule().module)
    add(OnboardingDataModule().module)
    add(OnboardingDomainModule().module)
    add(NetworkModule().module)
    add(CmpModule().module)
    add(HomeDataModule().module)
    add(HomeDomainModule().module)
    add(HomePresentationModule().module)
    add(DatabaseModule().module)
    add(MultiLangModule().module)
}

Koin starts once per process: Android calls initKoin from Application.onCreate, iOS from iOSApp.init (through startKoinAtLaunch() in MainViewController.kt). Never call it from a composable or from the view-controller factory: iPadOS can create a view controller per window, and a second startKoin throws. Both pass isDebug: Android from FLAG_DEBUGGABLE, iOS from Platform.isDebugBinary; Koin provides it as BuildEnvironment (core/domain).

KoinGraphTest (shared/src/androidHostTest/.../di/KoinGraphTest.kt) checks the whole graph: it fails, naming the type, when a class needs something no module in appModules() defines, for example a feature's presentation module added without its domain module. Run it with ./gradlew :shared:testAndroidHostTest; ./gradlew allTests runs every test on the JVM and the iOS simulator. Each module's commonTest already has kotlin-test, kotlinx-coroutines-test and Turbine.

3. Auto-Annotation

Once your module is set up, you can use Koin annotations to automatically register your classes. Common annotations include:

  • @Single: Creates a singleton definition.
  • @Factory: Creates a factory definition (new instance each time).
  • @KoinViewModel: Registers a ViewModel.

Network Architecture

Learn how to handle network requests with type-safe state management using Ktor and Flow. Coil's network fetcher lives here too: with network off, images load only from local sources.

1. Base URL

ApiConfig.kt holds two constants: a debug build uses the first, a release build the second. NetworkModule picks one with ApiConfig.baseUrl(environment).

ApiConfig.kt (core/network) 
/**
 * The API the app talks to. Debug builds use DEBUG_BASE_URL, release builds RELEASE_BASE_URL.
 * Keep the trailing slash and write request paths without a leading one.
 */
object ApiConfig {
    const val DEBUG_BASE_URL = "https://api.github.com/"
    const val RELEASE_BASE_URL = "https://api.github.com/"

    fun baseUrl(environment: BuildEnvironment): String =
        if (environment.isDebug) DEBUG_BASE_URL else RELEASE_BASE_URL
}

Keep the trailing / on both constants and write request paths without a leading one.

2. RestResult - State Management

We use a sealed class RestResult to represent the three states of a network request: Success, Error, and Loading. This provides type-safe state handling throughout your app. Error carries the reason as a DataError, so the screen can say what went wrong.

RestResult.kt (core/domain) 
sealed class RestResult<out T> {

    class Success<out T>(val result: T) : RestResult<T>()

    data class Error(val error: DataError) : RestResult<Nothing>()

    class Loading(val loading: Boolean) : RestResult<Nothing>()
}

The four reasons (core/domain):

DataError.kt (core/domain) 
sealed interface DataError {

    /** No connection, a timeout or an unknown host. */
    data object Network : DataError

    /** The server answered with [code], a status outside 2xx. */
    data class Http(val code: Int) : DataError

    /** The response body could not be read into the expected type. */
    data object Serialization : DataError

    /** Any other failure; [cause] is kept for logging. */
    data class Unknown(val cause: Throwable) : DataError
}

3. BaseRepository - Request Handler

The BaseRepository provides a reusable request function that wraps HTTP calls, turns every failure into RestResult.Error with its DataError, and rethrows CancellationException: a cancelled request (the screen was left, a newer search started) stops instead of becoming an error. All repositories extend this base class. (core/network is in the showcase and in blank projects with Network.)

BaseRepository.kt (core/network) 
open class BaseRepository {
    // CancellationException is rethrown: the caller was cancelled (the screen was left, a newer
    // search started) and has to stop here instead of receiving an error result
    suspend inline fun <reified T : Any> request(
        crossinline call: suspend () -> HttpResponse
    ): RestResult<T> = withContext(context = Dispatchers.IO) {
        try {
            call.invoke().asRestResult()
        } catch (e: CancellationException) {
            throw e
        } catch (e: Exception) {
            RestResult.Error(e.toDataError())
        }
    }
}

The client sets expectSuccess = true, so a status outside 2xx arrives as Ktor's ResponseException. toDataError() maps it and the other failures:

DataErrorMapper.kt (core/network) 
fun Throwable.toDataError(): DataError = when (this) {
    is ResponseException -> DataError.Http(code = response.status.value)
    is IOException -> DataError.Network
    is NoTransformationFoundException, is ContentConvertException -> DataError.Serialization
    is SerializationException -> DataError.Serialization
    else -> DataError.Unknown(cause = this)
}

4. Mapping Success Results

When you need to transform the response model (e.g., map API response to domain model), use the mapOnSuccess extension. It only transforms Success results, leaving Error and Loading unchanged.

RestResultExtension.kt (core/network) 
inline fun <T, R> RestResult<T>.mapOnSuccess(map: (T?) -> R): RestResult<R> = when (this) {
    is RestResult.Success -> RestResult.Success(map(result))
    is RestResult.Error -> this
    is RestResult.Loading -> this
}

5. Repository Implementation

Here's how to implement a repository. Use @Single to register it with Koin, extend BaseRepository, and use mapOnSuccess to transform responses (showcase: feature/onboarding/data). request already runs the call on Dispatchers.IO; no withContext is needed around it.

GithubRepositoryImpl.kt 
@Single(binds = [GithubRepository::class])
internal class GithubRepositoryImpl(private val httpClient: HttpClient) :
    BaseRepository(),
    GithubRepository {
    override suspend fun getUsers(username: String): RestResult<List<GithubUserListModel>> =
        request<GithubUserListResponse> {
            httpClient.request { reqUsers(username = username) }
        }.mapOnSuccess {
            githubUserListMapper(response = it)
        }
}

6. UseCase with buildDefaultFlow

UseCases call repositories and wrap the result in a Flow. The buildDefaultFlow extension automatically emits Loading(true) at the start, Loading(false) on completion, and catches errors (showcase: feature/onboarding/domain).

SearchGithubUsersUseCase.kt 
@Factory
class SearchGithubUsersUseCase(@Provided private val repository: GithubRepository) {
    operator fun invoke(username: String): Flow<RestResult<List<GithubUserListModel>>> = flow {
        val result = repository.getUsers(username = username)

        emit(result)
    }.buildDefaultFlow(Dispatchers.IO)
}

buildDefaultFlow Extension

This extension automates loading state management. It emits Loading(true) when the flow starts, turns an exception into Error(DataError.Unknown(cause)) (a CancellationException passes through, so a cancelled request never shows as a failure), and finally emits Loading(false) when complete.

UseCaseFlowExtension.kt (core/domain) 
inline fun <reified T> Flow<RestResult<T>>.buildDefaultFlow(
    dispatcher: CoroutineDispatcher,
    loading: Boolean = true
): Flow<RestResult<T>> = this.onStart {
    emit(RestResult.Loading(loading))
}.catch { cause ->
    // A cancelled request is not a failure: it goes on up instead of becoming an Error
    if (cause is CancellationException) throw cause
    emit(RestResult.Error(DataError.Unknown(cause = cause)))
}.onCompletion {
    emit(RestResult.Loading(false))
}.flowOn(dispatcher)

7. ViewModel - Handling States

In the ViewModel, use onSuccess, onError and onLoading to update the UI state. This is the showcase's OnboardingViewModel (feature/onboarding/presentation): typing searches once the query has not changed for SEARCH_DEBOUNCE_MILLIS (400 ms); a newer query, a retry or a cleared field cancels the search still running; a blank query sends no request. onError receives the DataError, which the state keeps until the next request starts.

OnboardingViewModel.kt 
@KoinViewModel
internal class OnboardingViewModel(
    @Provided private val navigationManager: NavigationManager,
    @Provided private val searchGithubUsers: SearchGithubUsersUseCase
) : CoreViewModel(),
    OnboardingActions {

    private val _uiState = MutableStateFlow(OnboardingUiState())
    val uiState: StateFlow<OnboardingUiState>
        get() = _uiState

    // ...

    override fun onRetry() {
        search(query = _uiState.value.query, debounceMillis = 0L)
    }

    // ...

    private fun search(
        query: String,
        debounceMillis: Long
    ) {
        searchJob?.cancel()
        if (query.isBlank()) {
            searchJob = null
            _uiState.update { it.copy(users = emptyList(), isLoading = false, error = null) }
            return
        }
        _uiState.update { it.copy(isLoading = false) }
        searchJob = viewModelScope.launch {
            delay(debounceMillis)
            _uiState.update { it.copy(isLoading = true, error = null) }
            safeFlowApiCall {
                searchGithubUsers.invoke(username = query)
            }.onSuccess { users ->
                _uiState.update { it.copy(users = users) }
            }.onError { error ->
                _uiState.update { it.copy(error = error) }
            }.onLoading { isLoading ->
                _uiState.update { it.copy(isLoading = isLoading) }
            }.collect()
        }
    }
}

The message comes from one place, errorMessage(error) next to the strings in core/multilang, which both showcase screens use (GitHub answers 403 or 429 once its request limit is used up):

8. Flow Extensions for State Handling

These three extensions (onSuccess, onError, onLoading) allow you to handle each RestResult state in a clean, functional way. They use transform to react to specific states while still emitting all results downstream.

FlowExtension.kt (core/domain) 
fun <T> Flow<RestResult<T>>.onSuccess(action: suspend (T) -> Unit): Flow<RestResult<T>> =
    transform { restResult ->
        if (restResult is RestResult.Success) {
            action.invoke(restResult.result)
        }
        emit(restResult)
    }

fun <T> Flow<RestResult<T>>.onError(action: suspend (DataError) -> Unit): Flow<RestResult<T>> =
    transform { restResult ->
        if (restResult is RestResult.Error) {
            action.invoke(restResult.error)
        }
        emit(restResult)
    }

fun <T> Flow<RestResult<T>>.onLoading(action: suspend (Boolean) -> Unit): Flow<RestResult<T>> =
    transform { restResult ->
        if (restResult is RestResult.Loading) {
            action.invoke(restResult.loading)
        }
        emit(restResult)
    }

How It Works

  • onSuccess: Executes the action when a Success result is emitted, typically used to update UI state with data.
  • onError: Executes the action with the DataError when an Error result is emitted; keep it in the state and show its message. A lambda that ignores the reason (onError { … }) still works.
  • onLoading: Executes the action when a Loading result is emitted, used to show/hide loading indicators.

All three extensions use transform to perform side effects while still emitting the original result, allowing you to chain multiple handlers together.

Logging with Kermit

Every project ships a small logging module: one setup, the same logger on Android and iOS.

What gets installed

Every project has the core/logging module, whatever options you generate it with. It brings Kermit to every module, and initKoin sets it up once with configureLogging(isDebug):

  • Debug builds write every level, Verbose and up.
  • Release builds write only Warn and Error.
  • Android writes to Logcat, iOS to OSLog.
  • Every tag starts with your project name: a Network logger writes as <Project>/Network.

How to log

Create one logger per class (or per file) with a short English tag, and pass the message as a lambda: a level that is off never builds the text.

CheckoutRepository.kt 
import co.touchlab.kermit.Logger

class CheckoutRepository(private val api: CheckoutApi) {
    private val log = Logger.withTag("Checkout")

    suspend fun pay(orderId: String): Boolean = try {
        api.pay(orderId)
        log.d { "Payment sent" }
        true
    } catch (e: PaymentException) {
        log.w(e) { "Payment failed" }
        false
    }
}

No build file change is needed: the convention plugin adds core/logging to every Kotlin Multiplatform module, including the ones you add later.

What the template logs

  • Failed requests, with the HTTP status code or the error type only.
  • In debug builds, one line per request (method, URL, status).
  • Ad and purchase warnings (consent, load and show failures, purchase errors).
  • One start-up line when Koin starts.

What never goes into a log

Tokens, API keys, request and response bodies, headers, and user data (names, IDs, e-mail addresses). Logs end up on devices and in bug reports, so write what happened, not the data. Keep exception messages out too: they often carry URLs or response text.

No println

The template has no println; use a Kermit logger instead. Detekt's ForbiddenMethodCall rule flags println, but only with type resolution (the IDE plugin and the type-resolving detekt tasks). A plain ./gradlew detekt runs without it and does not catch the call, so search for println( before a release.

Reading the logs

  • Android: in Android Studio's Logcat, filter with tag:<Project>/.
  • iOS: run from Xcode and read its console, or open Console.app and filter by the same tag prefix.

An offline banner, a retry when the connection comes back, and app update checks on Android and iOS without a server of your own.

ConnectivityMonitor

ConnectivityMonitor tells you whether the device is online: isOnline is a StateFlow<Boolean>.

  • Interface: in core/domain, so every feature module can inject it with @Provided.
  • Implementation: in core/network (connectivity/). Android uses ConnectivityManager (online = a validated internet connection, with the ACCESS_NETWORK_STATE permission); iOS uses NWPathMonitor.
  • It is there only when Network (Ktor) is on (the showcase always has it). With network off, core/network, the monitor and the permission are gone.

The offline banner

OfflineBanner (in shared) draws a thin "No connection" bar above the app while the device is offline; MainScreen shows it as the Scaffold's top bar. App updates (core/update)

Every project has the core/update module, whatever options you generate it with. MainScreen calls AppUpdateEffect() once; it checks at most once a day.

  • Android, suggested update: Play In-App Updates, the "flexible" flow. Play shows its own download screen; when the download is done, a dialog offers "Restart".
  • iOS, suggested update: the iTunes lookup for your bundle ID finds the App Store version; when it is newer, an "Update available" dialog opens the App Store page.
  • An app that was not installed from Google Play, or is not on the App Store yet, skips the check quietly.

Forced update. MIN_VERSION_URL is empty, so there is no forced update. Data Persistence with DataStore

Learn how to implement cross-platform data storage using DataStore with the expect/actual pattern.

What is DataStore?

DataStore is a data storage solution that allows you to store key-value pairs asynchronously. In Compose Multiplatform, we use the expect/actual pattern to handle platform-specific implementations for iOS and Android. The files below live in core/database (showcase, and blank projects with DataStore, Theming or MultiLanguage). With Theming, core/database also holds the saved theme choice (theme/).

1. Common Implementation

In your commonMain source set, define the expected platform-specific function and the shared factory function:

DataStore.kt (commonMain) 
expect fun getPlatformDataStore(): DataStore<Preferences>

fun createDataStore(producePath: () -> String): DataStore<Preferences> =
    PreferenceDataStoreFactory.createWithPath(
        corruptionHandler = null,
        migrations = emptyList(),
        produceFile = { producePath().toPath() }
    )

internal const val DATA_STORE_FILE_NAME = "multiplatform.preferences_pb"

You can customize the DATA_STORE_FILE_NAME to match your app's naming convention. The createDataStore function is a helper that both platforms will use.

2. Android Implementation

In your androidMain source set, provide the actual implementation using the Android Context:

DataStore.android.kt (androidMain) 
fun createAndroidDataStore(context: Context): DataStore<Preferences> = createDataStore(
    producePath = { context.filesDir.resolve(DATA_STORE_FILE_NAME).absolutePath }
)

private lateinit var dataStore: DataStore<Preferences>

actual fun getPlatformDataStore(): DataStore<Preferences> {
    if (::dataStore.isInitialized.not()) {
        val context: Context = getKoin().get()
        dataStore = createAndroidDataStore(context)
    }
    return dataStore
}

On Android, we lazily initialize the DataStore using the application Context retrieved from Koin. The file is stored in the app's internal files directory.

3. iOS Implementation

In your iosMain source set, provide the actual implementation using iOS file system APIs:

DataStore.ios.kt (iosMain) 
@OptIn(ExperimentalForeignApi::class)
private fun createIOSDataStore(): DataStore<Preferences> = createDataStore(
    producePath = {
        val documentDirectory: NSURL? = NSFileManager.defaultManager.URLForDirectory(
            directory = NSDocumentDirectory,
            inDomain = NSUserDomainMask,
            appropriateForURL = null,
            create = false,
            error = null
        )
        requireNotNull(documentDirectory).path + "/$DATA_STORE_FILE_NAME"
    }
)

private val dataStore: DataStore<Preferences> by lazy {
    createIOSDataStore()
}

actual fun getPlatformDataStore(): DataStore<Preferences> = dataStore

On iOS, we use NSFileManager to locate the Documents directory and store the DataStore file there. The instance is lazily initialized using Kotlin's lazy delegate.

4. Usage Example

Once the platform-specific implementations are in place, you can use DataStore in your common code by injecting it through Koin (DatabaseModule provides it with @Single fun provideDataStore() in DataStoreModule.kt). The theme preference is stored like this (core/database/.../theme/DarkModeManagerImpl.kt, in the showcase and in blank projects with Theming):

DarkModeManagerImpl.kt 
@Single(binds = [DarkModeManager::class])
class DarkModeManagerImpl(@Provided private val dataStore: DataStore<Preferences>) : DarkModeManager {

    // Stored by name: reordering or adding ThemeMode entries never changes a saved choice
    private val themeModeKey = stringPreferencesKey("themeMode")

    override fun getThemeMode(): Flow<ThemeMode> =
        dataStore.data.map { preferences -> ThemeMode.fromName(preferences[themeModeKey]) }

    override suspend fun setThemeMode(mode: ThemeMode) {
        dataStore.edit { preferences ->
            preferences[themeModeKey] = mode.name
        }
    }
}

From here, you can use standard DataStore APIs to read and write preferences. The platform-specific storage handling is completely abstracted away.

For structured data (tables, queries), see Room.

Local Database with Room

Store structured data in SQLite with Room KMP: one database, shared by Android and iOS.

What gets installed

Turning on Room Database adds the core/room module. It uses the bundled SQLite driver, so Android and iOS run the same SQLite and need no extra linker flag. The module holds:

  • AppDatabase: the app's one Room database, with its entity list and version.
  • DatabaseFactory.kt: builds the database with the bundled driver; queries run on Dispatchers.IO.
  • di/RoomModule.kt: Koin provides the database and every DAO. A module that uses a DAO takes it with @Provided.
  • schemas/: the exported schema of every database version.

Add a table

A table is an entity and a DAO, each in its own package. List the entity in @Database(entities = ...), add an abstract function for the DAO to AppDatabase and a @Single provider below it. This is the showcase's favorites table:

favorites/FavoriteUserEntity.kt (core/room, commonMain) 
@Entity(tableName = "favorite_users")
data class FavoriteUserEntity(
    @PrimaryKey val login: String,
    val avatarUrl: String,
    val name: String?,
    val addedAt: Long
)

favorites/FavoriteUserDao.kt (core/room, commonMain) 
@Dao
interface FavoriteUserDao {
    @Query("SELECT * FROM favorite_users ORDER BY addedAt DESC")
    fun observeAll(): Flow<List<FavoriteUserEntity>>

    @Query("SELECT EXISTS(SELECT 1 FROM favorite_users WHERE login = :login)")
    fun observeIsFavorite(login: String): Flow<Boolean>

    @Upsert
    suspend fun upsert(user: FavoriteUserEntity)

    @Query("DELETE FROM favorite_users WHERE login = :login")
    suspend fun deleteByLogin(login: String)
}

AppDatabase.kt (core/room, commonMain) 
// The app's Room database. To add a table: an @Entity and a @Dao in their own package, the entity in
// `entities`, an abstract function for the DAO and a @Single provider below. Changing a table needs a
// new `version` and a migration; core/room/schemas/ keeps every version's schema (commit it).
@Database(
    entities = [FavoriteUserEntity::class],
    version = 1,
    exportSchema = true
)
@ConstructedBy(AppDatabaseConstructor::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun favoriteUserDao(): FavoriteUserDao
}

// Room generates the actual object for each platform (KSP)
@Suppress("KotlinNoActualForExpect")
expect object AppDatabaseConstructor : RoomDatabaseConstructor<AppDatabase> {
    override fun initialize(): AppDatabase
}

@Single
fun provideFavoriteUserDao(database: AppDatabase): FavoriteUserDao = database.favoriteUserDao()

@Suppress("KotlinNoActualForExpect") is there because Room (KSP) generates the actual object for each platform, so the compiler sees an expect with no actual in your sources. The DAO provider lives in the same module as the database, so it takes no @Provided.

Version, migrations and schemas

Once the app has shipped, changing a table needs a higher version and a migration (autoMigrations or a Migration), or users with an older database lose their data. Room writes the schema of each version to core/room/schemas/<package>.core.room.AppDatabase/<version>.json. Commit these files: they are what migrations are checked against.

        favoriteUserDao.observeAll().map { rows -> rows.map { it.toFavoriteUserModel() } }

        favoriteUserDao.observeIsFavorite(login = login)

        favoriteUserDao.upsert(user = user.toFavoriteUserEntity(addedAt = Clock.System.now().toEpochMilliseconds()))
    }

    override suspend fun remove(login: String) {
        favoriteUserDao.deleteByLogin(login = login)
    }
}

Theming

Light, Dark and System modes through a Material theme built from your color palette; the user's choice is saved with DataStore.

Overview

Theming has three parts. core/designsystem/.../theme/ holds the color palette (CustomColorsPalette) and KtTheme, which turns the palette into a Material colorScheme. core/database/.../theme/ holds DarkModeManager, which saves the user's Light/Dark/System choice in DataStore (so choosing Theming for a blank project also adds DataStore). shared/.../AppTheme.kt applies that choice, and MainScreen wraps the whole app in AppTheme { ... }. Material components you add without explicit colors (Text, Button, CircularProgressIndicator, Card) follow the theme.

A blank project without Theming still has AppTheme.kt: a plain MaterialTheme that follows the system's light/dark setting with Material's baseline light and dark colors, without DataStore. Put your own colors in AppTheme.kt; do not add a second MaterialTheme. If your design has a single color mode, use its color scheme for both light and dark (or drop the isSystemInDarkTheme() check) and give the Android window the same background (below).

On Android the window behind the first frame follows the device too (Theme.App in res/values/themes.xml and res/values-night/themes.xml), so a dark-mode device never flashes white at launch. When you change the theme's background color, update window_background in both files; a single-mode app sets both to its background (or deletes values-night/themes.xml). Known limit: if the user picked the opposite of the device's mode, the first frame or two show the device's mode, because DataStore loads the saved choice asynchronously.

1. DarkModeManager

2. Implementation with DataStore

The choice is stored by name (mode.name), so reordering or adding modes never changes a saved choice; an unknown or missing value reads as SYSTEM.

enum class ThemeMode {
    LIGHT,
    DARK,
    SYSTEM;

    companion object {
        fun fromName(name: String?): ThemeMode = entries.firstOrNull { it.name == name } ?: SYSTEM
    }
}

Projects generated before this release keep DarkModeManager in core/designsystem/.../darkmode/ and save the mode as a number (intPreferencesKey("themeMode")). If you switch such an app to names, use a new key (for example themeModeName): reading the old number as text fails.

3. KtTheme: palette to Material

KtTheme picks the light or dark palette, provides it as LocalColorsPalette and applies MaterialTheme with a color scheme derived from it: background and surface from backgroundColor, onBackground and onSurface from textBlack, onSurfaceVariant from textGray, primary from tintBlack, onPrimary from backgroundColor, outline from textFieldUnFocusedBorder. Other roles keep Material's light or dark defaults. Add typography and shapes to its MaterialTheme call.

KtTheme.kt 
@Composable
fun KtTheme(
    darkTheme: Boolean,
    content: @Composable () -> Unit
) {
    val palette = if (darkTheme) OnDarkColorsPalette else OnLightColorsPalette
    CompositionLocalProvider(LocalColorsPalette provides palette) {
        MaterialTheme(colorScheme = colorSchemeFor(palette, darkTheme), content = content)
    }
}

internal fun colorSchemeFor(
    palette: CustomColorsPalette,
    darkTheme: Boolean
): ColorScheme = (if (darkTheme) darkColorScheme() else lightColorScheme()).copy(
    primary = palette.tintBlack,
    onPrimary = palette.backgroundColor,
    background = palette.backgroundColor,
    onBackground = palette.textBlack,
    surface = palette.backgroundColor,
    onSurface = palette.textBlack,
    onSurfaceVariant = palette.textGray,
    outline = palette.textFieldUnFocusedBorder
)

4. AppTheme

shared/.../AppTheme.kt turns the saved mode into light or dark; SYSTEM follows the device.

AppTheme.kt 
@Composable
internal fun AppTheme(
    darkModeManager: DarkModeManager = koinInject(),
    content: @Composable () -> Unit
) {
    val themeModeFlow = remember(darkModeManager) { darkModeManager.getThemeMode() }
    val themeMode by themeModeFlow.collectAsState(initial = ThemeMode.SYSTEM)
    val darkTheme = when (themeMode) {
        ThemeMode.LIGHT -> false
        ThemeMode.DARK -> true
        ThemeMode.SYSTEM -> isSystemInDarkTheme()
    }
    KtTheme(darkTheme = darkTheme, content = content)
}

Multi-Language Support

Implement dynamic language switching with persistent user preferences and system language detection.

Overview

The multi-language system is built on top of DataStore, allowing users to select their preferred language (or use system default) with preferences persisted across app sessions. The system uses a type-safe resource model for managing translations.

1. LanguageManager Interface

The language management is handled through a singleton LanguageManager interface:

LanguageManager.kt 
interface LanguageManager {
    val currentResources: StateFlow<StringResourcesUiModel>

    fun getCurrentLanguageFlow(): Flow<AppLanguage>
    suspend fun setLanguage(language: AppLanguage)
    suspend fun setSystemLanguage()
}

2. Implementation with DataStore

The implementation persists language preferences and manages resource updates:

LanguageManagerImpl.kt 
@Single(binds = [LanguageManager::class])
class LanguageManagerImpl(@Provided private val dataStore: DataStore<Preferences>) : LanguageManager {

    private val selectedLanguageKey = stringPreferencesKey("selectedLanguage")

    // Starts from the device language; setSystemLanguage() then applies a saved choice.
    private val _currentResources = MutableStateFlow(resourcesFor(AppLanguage.SYSTEM))
    override val currentResources: StateFlow<StringResourcesUiModel> =
        _currentResources.asStateFlow()

    override fun getCurrentLanguageFlow(): Flow<AppLanguage> = dataStore.data.map { prefs ->
        val storedCode = prefs[selectedLanguageKey] ?: AppLanguage.SYSTEM.code
        AppLanguage.fromCode(storedCode)
    }

    override suspend fun setLanguage(language: AppLanguage) {
        dataStore.edit { prefs ->
            prefs[selectedLanguageKey] = language.code
        }

        _currentResources.update { resourcesFor(language) }
    }

    override suspend fun setSystemLanguage() {
        val prefs = dataStore.data.firstOrNull()
        val selectedLanguage = AppLanguage.fromCode(code = prefs?.get(selectedLanguageKey))

        _currentResources.update { resourcesFor(selectedLanguage) }
    }

    // SYSTEM follows the device; a device language without a translation falls back to English.
    private fun resourcesFor(language: AppLanguage): StringResourcesUiModel {
        val active = if (language == AppLanguage.SYSTEM) {
            AppLanguage.fromCode(getDeviceLanguageCode())
        } else {
            language
        }
        return languageResources[active] ?: fallbackResources
    }
}

How It Works

  • setSystemLanguage(): Called on app startup to load the saved language preference
  • setLanguage(): Updates the language preference and loads the appropriate resource model
  • getCurrentLanguageFlow(): Returns a Flow of the current language for settings UI
  • currentResources: StateFlow that provides the active string resources to the UI
  • fallbackResources: English. Used for device languages without a translation, so no string is ever shown empty

3. Device Language Detection

To detect the device's system language, we use the expect/actual pattern for platform-specific implementations. Each source set of core/multilang has its own language/DefaultLanguage.kt.

In-app review

Every project can ask for a store rating with the system dialog, on Android and iOS.

What gets installed

Every project has the core/review module, whatever options you generate it with:

  • Android: Google Play In-App Review.
  • iOS: the StoreKit rating dialog.
  • ReviewPrompter counts positive moments and decides when to ask.
  • ReviewRequestEffect() in MainScreen hands each request to the platform. Keep that call.

How to use it

Inject ReviewPrompter and call recordPositiveEvent() right after a positive moment (an order placed, a favorite added). The first request comes on the 3rd event, then on every 10th (3, 13, 23, …). The count survives app restarts.

) : ViewModel() {
    fun onPaymentSucceeded() {
        // Right after the good moment, never at launch or in the middle of a task
        reviewPrompter.recordPositiveEvent()
    }
}

No build file change is needed: the convention plugin adds core/review to every feature presentation module, including the ones you add later.

"Rate the app"

For a "Rate the app" row, call openStorePage(). On Android it opens your app's Play Store page, found from the package name. On iOS it opens the App Store review page once you fill in APP_STORE_ID; while it is empty, the system rating dialog is asked for instead.

Ads with AdMob

Banner, interstitial and rewarded ads with Google's test IDs, behind the consent flow (UMP, then App Tracking Transparency on iOS).

What is included

With Ads (AdMob) on, the project gets core/ads and the ads/ package of feature/monetization: an ads demo screen that opens from Settings → Ad examples in the showcase, and from the Ad examples button on the start screen of a blank project. Android uses Google's GMA Next-Gen SDK (ads-mobile-sdk) and UMP; iOS uses the Google Mobile Ads SDK as a Swift package (the Next-Gen SDK is Android-only).

In the Next-Gen SDK, load and full-screen callbacks arrive off the main thread. AdsController handles this for you: it starts the SDK off the main thread and shows full-screen ads from the main thread, so your code calls it like any other suspend API.

Banner, interstitial and rewarded

BannerAd() draws a banner. rememberAdsController() returns an AdsController that gathers consent and shows full-screen ads. Call gatherConsent() first and request ads only once the returned ConsentStatus has canRequestAds set; each show call suspends until the ad is closed and returns an AdResult (Dismissed, Rewarded(amount, type) or Failed(reason)).

AdsDemoScreen.kt (sketch) 
@Composable
fun AdsDemoScreen(viewModel: AdsDemoViewModel = koinViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    val controller = rememberAdsController()

    // Consent first: no ad is requested before it. A recreated screen asks again
    // only while no answer has reached the ViewModel.
    LaunchedEffect(viewModel, controller) {
        if (!viewModel.uiState.value.consentResolved) {
            viewModel.onConsentResult(controller.gatherConsent())
        }
    }

    Column {
        if (uiState.consentReady) BannerAd()
        Button(
            enabled = uiState.consentReady,
            onClick = { viewModel.runAd { controller.showInterstitial() } }
        ) {
            Text("Show interstitial")
        }
        Button(
            enabled = uiState.consentReady,
            onClick = { viewModel.runAd { controller.showRewarded() } }
        ) {
            Text("Watch rewarded ad")
        }
    }
}
AdsDemoViewModel.kt (sketch) 
data class AdsDemoUiState(
    val consentResolved: Boolean = false,
    val consentReady: Boolean = false,
    val coins: Int = 0
)

class AdsDemoViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(AdsDemoUiState())
    val uiState: StateFlow<AdsDemoUiState> = _uiState.asStateFlow()

    fun onConsentResult(status: ConsentStatus) {
        _uiState.update { it.copy(consentResolved = true, consentReady = status.canRequestAds) }
    }

    // viewModelScope outlives the screen, so an ad on screen during a rotation still
    // delivers its result; one not yet opened when the screen is recreated is cancelled
    fun runAd(show: suspend () -> AdResult) {
        viewModelScope.launch {
            val result = show()
            if (result is AdResult.Rewarded) {
                _uiState.update { it.copy(coins = it.coins + result.amount) }
            }
        }
    }
}

Both blocks are sketches of the demo, which also handles premium users, a busy flag and the privacy options entry, and routes clicks to the screen through a command channel. The ViewModel holds the consent result as state (consentResolved), so a recreated screen (rotation, dark mode, language) does not ask again once an answer has arrived. It runs each show call in viewModelScope: the result of an ad already on screen still arrives after a rotation, while an ad that has not opened when its screen is recreated or left is cancelled; the call then ends with a CancellationException and returns no AdResult.

Launching an ad from rememberCoroutineScope() would lose its result when the screen is recreated; keep show calls in the ViewModel.

Consent

AdsController.gatherConsent() asks for consent with Google's User Messaging Platform (UMP), then, on iOS, with App Tracking Transparency, and starts the Mobile Ads SDK once ads may be requested. The demo gathers consent the first time the ads screen opens; a real app usually asks at launch, before the first ad screen.

Debug builds force the EEA debug geography (ConsentDebugSettings on Android, DebugSettings in AdsBridge.swift) so the form always shows; release builds use the user's real location. Emulators and simulators are test devices; on a physical device the debug geography also needs the device's test ID (addTestDeviceHashedId on Android, testDeviceIdentifiers on iOS).

In-App Purchases with RevenueCat

A custom Compose paywall on a small purchases API and a premium entitlement, wired to a Test Store key so purchases are simulated and nothing is charged.

What is included

With In-App Purchases (RevenueCat) on, the project gets two modules:

  • core/purchases: PurchasesKeys, the PurchasesManager interface (offer(), purchase(packageId), restore(), isPremium) and its RevenueCat implementation (Purchases KMP). App code never imports a RevenueCat type. RevenueCat is configured the first time Koin creates the manager (at launch, by FirstLaunchPaywall).
  • feature/monetization: the paywall/ package (a plain Compose screen, its ViewModel, navigation and FirstLaunchPaywall). In the showcase it opens from Settings → Premium; in a blank project the start screen lists a Premium button.

Test Store key

revenueCatApiKey (PurchasesKeys.android.kt and PurchasesKeys.ios.kt) is a RevenueCat Test Store key of the cmpose demo project. Purchases made with it are simulated by RevenueCat: no App Store or Play Store account is needed and nothing is charged. While it is in use, the app logs a warning when RevenueCat is configured, at launch: FirstLaunchPaywall in MainScreen is the first to need PurchasesManager.

Release builds

RevenueCat's SDK closes a release build that is configured with a Test Store key. So a release build that still has the Test Store key leaves RevenueCat unconfigured (PurchasesManager.isAvailable is false, nobody is premium) and the paywall shows a message that purchases are disabled in release builds instead. Debug builds use the Test Store key as usual; a release build with your own platform keys configures RevenueCat normally.

PurchasesKeys.kt 
// core/purchases/.../PurchasesKeys.kt (revenueCatApiKey: PurchasesKeys.android.kt and PurchasesKeys.ios.kt)
object PurchasesKeys {
    fun isTestStoreKey(apiKey: String): Boolean = apiKey.startsWith("test_")

    // Debug builds take any key; release builds only a platform key
    fun canConfigure(apiKey: String, isDebug: Boolean): Boolean = isDebug || !isTestStoreKey(apiKey)
}

Paywall and the premium entitlement

The paywall is a plain Compose screen (PaywallScreen.kt) on PurchasesManager: the plans of the current offering with the store's prices (annual selected, with its saving and monthly price), Continue, Restore purchases, Not now and your privacy policy and terms links (core/about). It is deliberately simple: redraw it in your app's design and keep PaywallViewModel, which loads the offer, buys or restores and closes the screen after a successful purchase or a restore that brings premium back.

The purchases API

offer() returns the current offering as plain models (PaywallOffer, PaywallPackage: id, PackagePeriod, price, monthly price of annual and weekly plans, annual saving in percent, free trial), or null without RevenueCat or offline. purchase(packageId) and restore() return a PurchaseResult: Success (isPremium follows), Cancelled (show nothing) or Error(message) (a short text to show). restore() without a purchase is Error("No purchases to restore").
